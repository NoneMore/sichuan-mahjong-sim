# 启发式策略成本归因

## 结论

第一次启发式策略优化应优先关注 **`policy::analysis::suit_table` 的逐花色精确 DP 计算**，而不是哈希、分配器或规则判定。

在 `heuristic-benchmark-v1` 四席自对弈中：

- 正式批次约 **99.4%** 的墙钟时间用于 `Policy::choose`，负载主要受策略计算限制。
- `suit_table` 占采样工作线程样本的 **80.70%**；重复运行、不同种子、较长批次、不同构建和采样方式下为 **76.85–81.78%**。
- 完整调用栈表明，主要成本沿 `ukeire → DistanceEvaluator::deficit → suit_table` 路径发生。

这足以确定首要优化方向，但不说明哪种改法最好。本研究未修改生产 Rust、未实施优化，也不承诺任何加速比。

## 测量条件

- 源码：`d8aceba715741dd956306106363360091259f524`，测量时无源码改动。
- 环境：Windows 10 Pro 19045，AMD Ryzen 7 3700X，8 核 16 线程；rustc 1.98.0、Cargo 1.98.0，`x86_64-pc-windows-msvc`。
- 工作负载：现有 `examples/heuristic_bench.rs`，协议 `heuristic-benchmark-v1`。每阶段新建一个 Runner 和四席策略，阶段内跨局复用；每局决策上限 10,000。未另建驱动入口。
- 基准使用默认 release 构建；采样构建增加 `-C debuginfo=2`，主要采样另加 `-C force-frame-pointers=yes`，并以不加该选项的构建交叉检查。
- 所有性能运行串行执行，不与构建或测试重叠；未绑定 CPU，其他系统活动未严格控制。

## 关键证据

### 1. 策略计算主导正式批次

默认 release 构建，正式 2,000 局、预热 20 局。表中为中位数，括号为范围。

| 指标 | 首种子 7，5 次 | 首种子 10007，3 次 |
| --- | ---: | ---: |
| 决策数 | 113,841 | 115,351 |
| 正式批次耗时（秒） | 16.780（16.329–17.298） | 17.061（16.939–17.123） |
| 策略累计耗时（秒） | 16.675（16.230–17.186） | 16.956（16.838–17.017） |
| 规则累计耗时（秒） | 0.0817 | 0.0824 |
| 吞吐量（局/秒） | 119.19 | 117.22 |
| 策略耗时 / 批次耗时 | 99.36–99.40% | 99.38–99.40% |

这些是正式批次的墙钟计时，不是下文的采样权重；两种百分比不能直接等同。

### 2. 首要热点具有稳定的领先幅度

现有 WPR/xperf 在本机权限下无法采样，因此使用一次性的外部线程采样脚本，不修改策略源码。脚本捕获工作线程指令地址，用 Windows unwind 信息展开调用栈，以 PDB 内联记录区分被内联的函数。采样环境为 64 位 CPython 3.12.10、dbghelp 10.0.26100.9457。

低扰动方式在捕获上下文后立即恢复线程；完整栈检查方式则保持线程暂停直到栈展开结束。

| 配置 | 样本数 | `suit_table` self 占比 |
| --- | ---: | ---: |
| 2,000 局，种子 7，无预热 | 3,524 | 79.97% |
| 同配置重复 | 3,519 | 80.90% |
| 2,000 局，种子 10007，无预热 | 3,648 | 79.66% |
| 5,000 局，种子 777，无预热 | 9,126 | 80.91% |
| 2,000 局，种子 7，预热 20 局 | 3,551 | 81.78% |
| 2,000 局，种子 7，不强制 frame pointer | 3,591 | 81.37% |
| 2,000 局，种子 7，暂停期间展开完整栈 | 3,184 | 76.85% |

前五次合计 **23,368 个样本**：`suit_table` self 为 18,859 个（80.70%），哈希为 4.33%，分配器为 3.06%，七对子与花色组合计算合计约 4.0%。这些都是**整个采样工作线程窗口的份额**，不是策略内部的归一化百分比。

`suit_table` 是策略私有分析路径；哈希、分配和规则函数则可能共享，不能仅凭函数名全部归入策略。各配置中次高成本桶（哈希）均不超过 4.84%，与首要热点的差距远大于本次观测到的波动，因此无需强行保留多个并列候选。

### 3. 调用上下文支持这一归因

保持线程暂停的检查获得 97.6% 的完整栈，共 3,184 个样本：

| 调用路径 | Inclusive 占比 |
| --- | ---: |
| `HeuristicPolicy::choose` | 96.98% |
| `DistanceEvaluator::deficit` | 94.28% |
| `rank_discards` | 90.17% |
| `ukeire` | 78.42% |

Inclusive 包含子调用，以上数值不能相加。在 2,666 个外层 self 符号为 `deficit` 的样本中，其直接调用者为 `ukeire` 的占 80.95%，为 `rank_discards` 的占 18.53%。这支持将主要成本定位到有效进张评估中的反复 deficit 计算，而非仅仅候选弃张比较。

同一检查中，154 个哈希样本和 95 个分配器样本均位于 `choose` 调用链下；64 个共享规则/和牌判定样本中有 59 个可确认在策略链下，另 5 个栈截断，无法归属。低扰动采样的栈多数不完整，故不以它对共享函数作精确的策略内排序。

## 可信度与局限

- **窗口不同。** 采样不是正式批次的精确起止窗口：启动等待、线程选择和符号初始化使开头约 0.8–2.2% 的批次未被采到，末尾可能包含少量输出。无预热配置消除了预热混入；20 局预热配置的采样窗口为 17.704 秒，短于正式批次 17.887 秒，表明采样在正式阶段开始后才启动。较长批次及预热配置都未改变热点判断。
- **采样有扰动。** 低扰动方式实际约每 4.5–5.1 毫秒采一个样本，栈完整率约 43%，只用于 self 热点判断。保持暂停的方式约每 12.2 毫秒一个样本，批次耗时增加到非采样的 2.25–2.29 倍，仅用于调用上下文及方法交叉检查；其热点份额有所变化，但不足以改变优先级。
- **不是精确延迟。** self 指样本指令地址所在函数，inclusive 指栈中包含该函数。优化构建的内联与符号映射存在精度限制；这些权重不是单次决策延迟，也不是跨机器保证。未进行足以量化符号和 frame-pointer 构建开销的交错实验。
- **行为检查有限。** 同一正式种子范围下，普通构建、符号构建及采样运行的决策数、终局数、得分和胜局聚合结果一致。这支持工作负载可比，但不是逐动作等价证明。

## 复现

从上述源码提交构建和运行默认基准，首种子 7 重复 5 次、10007 重复 3 次：

```sh
cargo build --release --example heuristic_bench
target/release/examples/heuristic_bench.exe --games 2000 --seed 7 --warmup 20
target/release/examples/heuristic_bench.exe --games 2000 --seed 10007 --warmup 20
```

函数级采样、符号解析及聚合命令见归档 Change 的[一次性复现材料](../../specs/archive/heuristic-cost-attribution/tools/README.md)。按上表变更局数、首种子、预热、frame-pointer 构建选项及暂停方式，即可重新采集同类证据并独立判断热点。不要求复现相同绝对耗时或百分比。

本研究对应的[设计](../../specs/archive/heuristic-cost-attribution/design.md)已完成；后续优化需另行验证正确性与实际收益。
